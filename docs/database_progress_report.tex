\section{Introduction}
% ══════════════════════════════════════════════════════════════════════

This document reports the progress made on the \textbf{Data Layer} (Role~A) of the Saknny platform. The work covers the initial database infrastructure setup, the creation of the foundational SQLAlchemy ORM models, and the establishment of the schema contract that guides all downstream API development.

The implementation follows the project's governance rules as defined in:
\begin{itemize}[noitemsep]
    \item \texttt{governance/ownership.md} -- role boundaries and file ownership
    \item \texttt{governance/workflow.md} -- development workflow and safety rules
    \item \texttt{governance/api\_patterns.md} -- API response and ID conventions
    \item \texttt{governance/ai\_rules.md} -- AI agent behavioral constraints
\end{itemize}

All database design decisions are grounded in the \textbf{First Term Report V1.0}, Chapter~3 (System Analysis and Design), specifically Section~3.5 (Data Design) and the Data Dictionary (Section~3.5.4).

\subsection{Database Connection Layer}

The file \texttt{backend/app/core/database.py} provides:

\begin{itemize}[noitemsep]
    \item A SQLAlchemy \texttt{Engine} connected to the PostgreSQL instance.
    \item A \texttt{SessionLocal} factory for creating database sessions.
    \item A \texttt{Base} declarative class from which all ORM models inherit.
    \item A \texttt{get\_db()} dependency function for FastAPI injection.
\end{itemize}

\subsection{Initialization Script}

The script \texttt{scripts/init\_db.py} creates all tables registered with the \texttt{Base} metadata. It is idempotent -- running it multiple times will not duplicate or alter existing tables.

\section{Verification Workflow}
% ══════════════════════════════════════════════════════════════════════

The verification process follows the workflow defined in the report's event tables:

\begin{enumerate}
    \item \textbf{Student Registration:} The student creates an account with email, password, faculty ID, and personal details. The password is hashed using bcrypt before storage.

    \item \textbf{Document Upload:} The student uploads a college ID image. The file is saved to the filesystem at:
    \begin{center}
        \texttt{uploads/verification\_docs/<student\_id>/<uuid>\_<filename>}
    \end{center}
    A row is inserted into \texttt{verification\_documents} with \texttt{status = `pending'}.

    \item \textbf{Fraud Detection (Optional):} The system's Policy Engine may automatically flag suspicious uploads by setting \texttt{is\_flagged = TRUE} and recording the \texttt{flag\_reason}.

    \item \textbf{Admin Review:} An administrator reviews the document from the verification queue. They either:
    \begin{itemize}[noitemsep]
        \item \textbf{Approve:} Sets \texttt{status = `approved'}, records \texttt{reviewed\_by} and \texttt{review\_date}.
        \item \textbf{Reject:} Sets \texttt{status = `rejected'}, records the \texttt{rejection\_reason}.
    \end{itemize}

    \item \textbf{Eligibility Approval:} Once all required documents are approved, the admin sets \texttt{students.enroll\_status = TRUE}, enabling the student to submit housing applications.
\end{enumerate}

\begin{table}[h!]

\end{itemize}

\section{Business Rules and Constraints}
% ══════════════════════════════════════════════════════════════════════

The following business rules are enforced at the database level:

\begin{enumerate}
    \item \textbf{Unique Identifiers:} All entities use numeric auto-incrementing IDs, as specified in the API patterns governance document.
    \item \textbf{Unique Emails:} Both \texttt{admins.email} and \texttt{students.email} have UNIQUE constraints to prevent duplicate accounts.
    \item \textbf{Unique Faculty ID:} \texttt{students.faculty\_id} has a UNIQUE constraint ensuring each university ID maps to exactly one student account.
    \item \textbf{Enrollment Gate:} \texttt{students.enroll\_status} defaults to \texttt{FALSE} and must be set to \texttt{TRUE} by an admin before a student can submit a housing application.
    \item \textbf{Verification Gate:} A student cannot be marked as enrolled until at least one verification document has been approved.
    \item \textbf{Password Security:} All passwords are stored as bcrypt hashes (VARCHAR(255) to accommodate the 60-character bcrypt output with headroom).
    \item \textbf{Referential Integrity:} Foreign key constraints ensure no orphaned records can exist in \texttt{verification\_documents}.
\end{enumerate}

\section{Next Steps}
% ══════════════════════════════════════════════════════════════════════

The following tables remain to be implemented to complete the full database schema as defined in the First Term Report:

\begin{enumerate}
    \item \texttt{applications} -- Housing application submissions (FK $\rightarrow$ students, buildings)
    \item \texttt{application\_reviews} -- M:N link table between admins and applications
    \item \texttt{buildings} -- Dormitory buildings with gender segregation
    \item \texttt{rooms} -- Individual rooms within buildings with capacity tracking
    \item \texttt{allocations} -- Final bed assignments (FK $\rightarrow$ students, rooms, admins)
    \item \texttt{audit\_logs} -- Cross-cutting audit trail for sensitive changes
\end{enumerate}

Once the remaining tables are implemented, the schema contract will be updated and Role~B (API Layer) can proceed with the full REST API implementation.
