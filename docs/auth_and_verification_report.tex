\section{Introduction}
% ══════════════════════════════════════════════════════════════════════

This document reports the progress made on both the \textbf{Data Layer} (Role~A) and \textbf{API Layer} (Role~B) of the Saknny platform. The work covers the initial database infrastructure setup, foundational SQLAlchemy ORM models, API contracts, and the complete backend API implementation for Authentication and Verification modules.

The implementation directly realizes the system requirements and workflows described in the \textbf{First Term Report V1.0}, Chapter 3 (specifically the Data Design, Data Dictionary, and Event Tables for Students and Admins).

The implementation strictly follows the project's governance rules as defined in:
\begin{itemize}[noitemsep]
    \item \texttt{governance/ownership.md} -- role boundaries and file ownership
    \item \texttt{governance/workflow.md} -- development workflow and safety rules
    \item \texttt{governance/api\_patterns.md} -- API response and ID conventions
\end{itemize}

\section{Database Schema (Role A)}
% ══════════════════════════════════════════════════════════════════════

Three tables have been created to support the \textbf{Authentication and Verification} modules.

\subsection{Table: \texttt{admins}}
Represents university staff members who manage the housing platform and review documents.
Columns include \texttt{admin\_id}, \texttt{name}, \texttt{email}, \texttt{password\_hash}, \texttt{role}, \texttt{created\_at}, and \texttt{updated\_at}.

\subsection{Table: \texttt{students}}
Represents students who use the platform.
Columns include \texttt{student\_id}, \texttt{faculty\_id}, \texttt{name}, \texttt{email}, \texttt{password\_hash}, \texttt{enroll\_status} (boolean gate set by Admin), \texttt{gender}, \texttt{home\_city}, \texttt{distance\_score}, and timestamps.

\subsection{Table: \texttt{verification\_documents}}
Tracks documents uploaded by students for identity and enrollment verification.
Columns include \texttt{doc\_id}, \texttt{student\_id} (FK), \texttt{doc\_type}, \texttt{file\_path}, \texttt{status} (pending/approved/rejected), \texttt{reviewed\_by} (FK $\rightarrow$ admins), \texttt{is\_flagged}, and timestamps.

% ══════════════════════════════════════════════════════════════════════
\section{API Implementation (Role B)}
% ══════════════════════════════════════════════════════════════════════

Following the Contract-Driven Development methodology, the API schema was strictly defined in \texttt{contracts/api/contracts.md} before implementation.

All APIs utilize a standardized response format:
\begin{lstlisting}[language=json]
{
  "success": true,
  "data": { ... },
  "error": null
}
\end{lstlisting}

\subsection{Authentication Endpoints}

\begin{itemize}[noitemsep]
    \item \textbf{\texttt{POST /api/v1/students/register}}: Allows students to create an account. Validates email and faculty ID uniqueness, hashes the password via bcrypt, and returns the new \texttt{student\_id}.
    \item \textbf{\texttt{POST /api/v1/auth/login}}: Unified login endpoint for both Students and Admins. Verifies the bcrypt hash and issues a stateless JWT access token containing the user's role and ID.
\end{itemize}

\subsection{Verification Endpoints}

These endpoints execute the verification workflow specified in the First Term Report Event Tables.

\begin{itemize}[noitemsep]
    \item \textbf{\texttt{POST /api/v1/students/\{id\}/documents}}: Authorized students can upload \texttt{multipart/form-data} (JPEG, PNG, PDF) identity documents (e.g., college ID). The files are securely saved to the filesystem at \texttt{uploads/verification\_docs/<student\_id>/<uuid>\_<filename>} and logged as \texttt{pending} in the database.
    
    \item \textbf{\texttt{GET /api/v1/admin/verifications?status=pending}}: Admins can retrieve the queue of pending documents uploaded by students.
    
    \item \textbf{\texttt{PUT /api/v1/admin/verifications/\{doc\_id\}}}: Admins approve or reject documents. 
    \textbf{Business Rule Execution:} When an admin approves a document, the API automatically verifies if the student has any remaining pending documents. If all documents are resolved, the student's \texttt{enroll\_status} is dynamically flipped to \texttt{TRUE}, enabling them to proceed to housing applications.
\end{itemize}

\section{Exception Handling \& Validation}
% ══════════════════════════════════════════════════════════════════════

The FastAPI application implements robust, centralized exception handling:
\begin{itemize}[noitemsep]
    \item \textbf{Validation Errors}: Pydantic validation failures (HTTP 422) are intercepted and rewritten into the standardized \texttt{\{"success": false, "error": "Validation error: ..." \}} format.
    \item \textbf{Internal Server Errors}: Uncaught exceptions (HTTP 500) are gracefully caught to prevent stack trace leakage and mapped to the standard error structure.
\end{itemize}

% ══════════════════════════════════════════════════════════════════════
\section{Security Mechanisms}
% ══════════════════════════════════════════════════════════════════════

\begin{enumerate}
    \item \textbf{Passwords:} Bcrypt hashing prevents plaintext password exposure.
    \item \textbf{JWT Tokens:} Cryptographically signed JSON Web Tokens ensure stateless, tamper-proof session management.
    \item \textbf{Role-Based Access Control (RBAC):} API dependencies (\texttt{get\_current\_student}, \texttt{get\_current\_admin}) enforce domain authorization to prevent privilege escalation.
\end{enumerate}
